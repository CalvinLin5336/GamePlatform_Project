GamePlatform 小組專題成果簡報——呈現規劃

一、簡報任務

預設觀眾：職訓成果發表的老師、同學，以及未來閱讀作品集的面試官。
預設用途：12～15 分鐘成果報告；即使沒有口頭講解，面試官快速翻閱也能理解。
核心訊息：本專題不是單一遊戲，而是一個把會員、遊戲管理、組隊公告、房間、即時通訊與多款遊戲串成完整流程的模組化遊戲平台。

簡報結束時，觀眾應能回答四個問題：
1. 這個平台解決什麼需求？
2. 使用者如何從登入一路進入遊戲？
3. 各模組、資料表與即時功能如何合作？
4. 團隊有哪些可實際操作、可驗證的成果？


二、敘事方式

不採用「A 組員做會員、B 組員做房間」的工作清單式介紹。
改採一條完整使用流程作為主線：

會員登入
→ 瀏覽遊戲與模式
→ 從大廳或組隊公告建立／加入房間
→ 等待成員並開始遊戲
→ 進入田忌撲克或問答遊戲
→ 即時同步狀態
→ 管理員維護會員與平台資料

每一張技術圖都必須服務這條主線，不為了展示技術而展示技術。


三、視覺方向

比例：16:9。
整體風格：沿用平台現有的深藍夜色介面，搭配藍紫色作為平台主色；Poker 頁面可使用綠色與金色作局部強調，但不改變整份簡報的視覺系統。

排版原則：
- 每頁只表達一個主要結論。
- 標題直接說結論，不使用「系統架構」「功能介紹」這類只有分類、沒有觀點的標題。
- 優先使用一張主要視覺；避免把投影片切成許多小卡片。
- 實機截圖要裁掉瀏覽器雜訊與開發工具，只留下與該頁結論有關的區域。
- 架構、流程、資料關係使用重新繪製的圖，不截 Eclipse 或 DB Browser 當主視覺。
- 程式碼只出現在 Poker 演算法頁，最多顯示 6～12 行關鍵片段。
- 所有文字以中文為主；類別、方法、API、JWT、WebSocket 等技術名稱保留英文。


四、建議投影片結構（15 頁）

第 1 頁｜封面
標題：GamePlatform 遊戲對戰平台
任務：讓觀眾立刻知道這是一個小組整合型專題。
畫面：平台代表畫面或遊戲入口畫面作全幅背景；保留專題名稱、組員、單位、日期。

第 2 頁｜我們想做的不是單一遊戲，而是一條完整的遊玩流程
任務：說明專題動機與目標。
畫面：將「找遊戲、找玩家、建立房間、開始遊戲」畫成一條簡短旅程，不放大段文字。

第 3 頁｜六個模組共同組成遊戲平台
任務：建立全貌。
內容：User、Game Management、Lobby、Board、Chat、Games（Poker／Quiz）。
畫面：平台為中心、模組向外展開的扁平架構圖；同時區分共用平台功能與個別遊戲。

第 4 頁｜前端、Spring Boot 與 SQLite 串起所有模組
任務：說明系統實際如何部署與溝通。
內容：HTML／CSS／JavaScript／jQuery／部分 React、REST API、WebSocket、Spring Boot、JPA／JDBC、SQLite、JWT。
畫面：瀏覽器 → 後端服務 → 資料庫的三層架構；模組標示在對應層，不製作 Logo 牆。

第 5 頁｜玩家可以從登入一路完成組隊、進房與遊戲
任務：以使用者角度呈現完整流程。
畫面：登入 → 大廳／公告 → 選遊戲與模式 → 建房／入房 → 等待 → 遊戲；使用 6 個節點以單一路徑呈現。

第 6 頁｜Game 與 GameMode 讓房間不必寫死遊戲規則
任務：說明模組化遊戲設計的核心。
內容：遊戲名稱、入口路徑、圖示、啟用狀態，以及模式的人數範圍與電腦玩家數。
畫面：Game → GameMode → Room → Game Page 的資料傳遞圖，搭配田忌撲克／問答遊戲範例。

第 7 頁｜資料模型同時支援會員、組隊、房間與多款遊戲
任務：呈現 ER Model，但避免一次塞入所有欄位。
畫面：以核心關係為主的 ER 圖；主線至少包含 users、roles、statuses、games、game_modes、rooms、room_players、team_posts、members、join_requests。次要欄位與 Quiz 題庫可淡化或分區。

第 8 頁｜JWT 讓不同頁面共享同一個登入身分
任務：說明會員驗證如何跨模組使用。
畫面：Login → JWT → Authorization Header → Security Filter → User／Lobby／Board／Poker。只解釋 JWT 在本專案中的用途，不上密碼學課。

第 9 頁｜組隊公告在成員到齊後建立房間並導向遊戲
任務：展示最具整合性的核心資料流。
畫面：以建立隊伍或核准加入為例，呈現 JavaScript → Controller → Service → Game Management／Lobby → SQLite → WebSocket 更新。這一頁取代大量 API 清單。

第 10 頁｜實際介面把平台流程連成一致體驗
任務：證明功能可操作。
畫面：使用 3～4 張經裁切的實機畫面，按流程排列：登入、大廳／公告、建立或加入房間、等待頁。畫面下方只寫動作，不寫功能長清單。

第 11 頁｜田忌撲克完成選牌、比牌與即時對戰流程
任務：呈現遊戲成果。
畫面：以一張清楚的 Poker 遊戲畫面為主，標示房間 ID、玩家名稱、目前輪次、選牌區與三輪結果；小圖可補玩家對戰／電腦模式。

第 12 頁｜統一強度值與組合搜尋完成 Poker 自動選牌
任務：提供全份簡報最主要的程式設計深度案例。
左側：determine_hand_strength()——將牌型、主要點數、踢腳牌與花色編碼成可直接比較的 long 強度值。
右側：find_best_cards()——從目前可用的牌中列舉本輪 3 張或 5 張組合，呼叫強度計算並保留最高分組合。
呈現：以流程與一組牌例為主，各附少量關鍵程式碼。明確說明這是目前輪次最佳組合，不是三輪整體安排。

第 13 頁｜平台可持續加入不同規則與介面的遊戲
任務：用 Quiz 證明 GamePlatform 不只服務 Poker。
畫面：Quiz 實機畫面＋Game Management 中的遊戲／模式資料；說明新遊戲可登錄入口、圖示及模式設定，再被大廳與公告選取。

第 14 頁｜跨模組整合透過測試與一致性檢查降低風險
任務：說明專題品質與解決過的困難。
內容：Git 合作與衝突、SQLite／JPA、JWT 身分串接、WebSocket 即時更新、Lobby 與遊戲資料交接。
證據：列出實際存在的後端整合測試、Poker 測試與前端測試；不宣稱沒有實際執行過的結果。

第 15 頁｜從會員到遊戲，平台已形成可擴充的完整流程
任務：收束成果並進入 Demo／Q&A。
畫面：回到第 2 頁的使用流程，將已完成節點全部點亮；保留 Demo 入口或 QR Code 的位置，不只放「Thank you」。


五、素材製作方式

實機截圖清單：
1. 登入／註冊頁。
2. 遊戲大廳或遊戲選擇畫面。
3. 組隊公告列表與遊戲／模式篩選。
4. 建立隊伍或建立房間表單。
5. 房間等待頁。
6. Poker 遊戲進行中畫面。
7. Quiz 問答畫面。
8. Admin 管理頁（若可正常登入與顯示資料）。

截圖一致性：
- 使用同一組測試名稱、相同瀏覽器寬度與相近資料量。
- 隱藏密碼、JWT、個資、瀏覽器書籤與無關分頁。
- 多人功能使用兩個測試帳號／工作階段；不能穩定重現的畫面不偽造。
- 截圖只作成果證據，重要流程仍重新繪製。

程式碼呈現：
- 不直接貼整個類別，也不以完全摺疊的方法清單解釋演算法。
- 從正式程式碼擷取少量片段到 PPT 素材，不為了截圖修改團隊原始碼。
- 使用中文註記 ①輸入、②處理、③輸出；一次只標示一個重點。
- determine_hand_strength() 與 find_best_cards() 各保留一個片段，其餘用流程圖和牌例說明。


六、內容界線

- 全份簡報以「團隊完成的平台」為主詞，不設個人成果頁。
- Poker 演算法作為模組技術亮點介紹，但投影片不寫個人署名；需要面試時可由負責人補充設計過程。
- 不把尚未完成的功能寫成已完成。
- 不用過多程式碼、API 表格、完整資料表欄位或套件 Logo 填滿頁面。
- 技術問題頁只選能證明團隊如何整合系統的案例，不變成錯誤紀錄清單。


七、目前採用的製作假設

- 簡報長度先以 15 頁、12～15 分鐘規劃。
- 同一份檔案兼顧成果發表與面試官事後閱讀。
- 無指定既有 PowerPoint 模板，因此視覺將延續現有 GamePlatform 深色介面。
- 後續以實際可執行頁面、程式與測試結果為準；盤點後如發現模組尚未接通，將調整用字與畫面，不製造不存在的成果。
